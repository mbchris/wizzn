# GitHub Issue Flow

End-to-end skill for turning a GitHub Issue into merged,
closed code — with a human checkpoint before each
irreversible step.

---

## Phase 0 — Resolve the Issue

Accept any of:
- A full GitHub issue URL
  `https://github.com/{{ORG}}/{{REPO}}/issues/{{N}}`
- A bare issue number `#N` (repo inferred from
  `gh repo view --json nameWithOwner`)
- No input → ask the user for the issue URL or number

```bash
# Infer current repo when only a number is given
gh repo view --json nameWithOwner -q .nameWithOwner

# Fetch the issue (fields cover title, body, labels,
# assignees, milestone, existing comments)
gh issue view {{N}} --json \
  title,body,labels,assignees,milestone,comments,state
```

Store: `ISSUE_NUMBER`, `ISSUE_TITLE`, `ISSUE_BODY`,
`ISSUE_URL`.

Derive `ISSUE_URL`:
```bash
gh issue view {{N}} --json url -q .url
```

---

## Phase 1 — Understand the Issue

Read and analyse the fetched JSON:

1. **Title + body** — state the problem or feature request
2. **Labels** — note `bug`, `enhancement`, `chore`, etc.
3. **Existing comments** — look for constraints,
   decisions, or prior implementation attempts
4. **Linked PRs** — check if a PR already addresses it:
   ```bash
   gh pr list --search "closes:#{{N}}" --state all \
     --json number,title,state
   ```
   If a closed/merged PR exists, inform the user and stop.

---

## Phase 2 — Explore the Codebase

Run only the searches needed to understand the change:

```bash
# List files relevant to the issue topic
git grep -l "{{keyword}}" -- . 2>/dev/null | head -20

# Recent changes in likely affected areas
git log --oneline -10 -- {{path}}
```

Goals:
- Identify entry points (files to touch)
- Understand current behaviour / data flow
- Surface related tests

Do **not** read every file — read only what is necessary
to produce a credible plan.

---

## Phase 3 — Write the Implementation Plan

Compose a plan comment in this structure:

```markdown
## Implementation Plan

**Issue:** #{{N}} — {{ISSUE_TITLE}}

### Problem Summary
<1-3 sentences. What is broken / missing and why.>

### Proposed Approach
<Describe the solution strategy at design level.
No code walls — reference file paths and function
names, not full implementations.>

### Files to Change

| File | Change |
|------|--------|
| `path/to/file` | <what changes and why> |

### New Files (if any)

| File | Purpose |
|------|---------|
| `path/to/new` | <what it contains> |

### Test Plan
- <How to verify the fix / feature manually>
- <Which existing tests to run / update>
- <New tests to write, if any>

### Out of Scope
<Anything deliberately excluded from this change.>

---
*Plan generated by AI — please review before confirming.*
```

**Always** post the plan as a comment immediately —
do not wait for the user to ask:

```bash
gh issue comment {{N}} --body "{{PLAN_BODY}}"
```

After posting, say to the user:

> "Do you approve implementation based on the design
> documented in {{ISSUE_URL}} ?"

**Stop here and wait for the user's response.**

---

## Phase 4 — Implement (after user confirms)

Only proceed after the user explicitly says something
like "yes", "go ahead", "looks good", "proceed", or
equivalent.

If the user requests changes to the plan, update the
comment and return to the end of Phase 3.

### 4a — Branch

```bash
# Create a branch named after the issue
git checkout -b issue-{{N}}-{{slug}}
```

`{{slug}}` = issue title lowercased, spaces → hyphens,
max 40 chars, no special chars.

### 4b — Implement

Follow the plan exactly. For each file in the plan:
1. Read the current content
2. Make the minimal, targeted change
3. Do not refactor unrelated code (refactoring protocol)

### 4c — Tests

Run the project's test suite after changes:

```bash
# Adapt to project's actual test command
# (check package.json / Makefile / README first)
npm test        # Node / pnpm projects
./gradlew test  # Gradle projects
pytest          # Python projects
```

Fix any test failures caused by the change before
proceeding.

### 4d — Commit

Use Conventional Commits format:

```bash
git add -p          # stage hunks interactively
git commit -m "fix(scope): short imperative summary

Closes #{{N}}"
```

---

## Phase 5 — Comment Final Summary and Present Result

### 5a — Post final summary comment to GitHub issue

**Always** post the final implementation summary comment to
the GitHub issue immediately after implementation completes —
do not wait for closing confirmation. This ensures the design
and changes are permanently documented on the issue even if
closing happens later.

Build the comment body using this template:

```markdown
## Implementation Summary

**Commit:** `{{COMMIT}}`
**Branch:** `{{BRANCH}}`

### What was done
<2-4 sentences describing the solution and
why this approach was chosen. Written for future
readers, not for the reviewer who confirmed it.>

### Files changed

| File | Change |
|------|--------|
| `path/to/file` | <one-line description> |

### Design decisions
<Bullet list of any non-obvious choices made
during implementation — alternatives considered,
trade-offs accepted, or constraints respected.
Omit this section if the change was straightforward.>

### Tests
<How the change was verified: which test suite
was run, what was added or updated.>

---
*Implemented by AI agent.*
```

Populate every field from actual data. Remove sections
that don't add value (e.g. no design decisions for
trivial changes).

Post the comment immediately:

```bash
COMMIT=$(git rev-parse --short HEAD)
BRANCH=$(git rev-parse --abbrev-ref HEAD)

gh issue comment {{N}} --body "{{COMMENT_BODY}}"
```

### 5b — Present the result and ask to close

Show the user:
- Files changed (`git diff --stat HEAD~1`)
- Test output summary
- A short description of what was done
- Note that the final summary was commented on `{{ISSUE_URL}}`

Then ask:

> "If everything looks fine from your side, shall I
> close the GitHub issue now?"

**Stop here and wait for the user's response.**

---

## Phase 6 — Close the Issue

Only after the user confirms in Phase 5 to close the issue:

```bash
gh issue close {{N}}
```

Then inform the user:

> "Issue #{{N}} is closed. Commit: \`{{COMMIT}}\`."

---

## Guardrails

- **Always post the implementation plan as a comment in Phase 3.**
- **Always post the final summary as a comment in Phase 5.**
- **Never implement before Phase 3 confirmation.**
- **Never close the issue before Phase 5 confirmation.**
- If `gh` is not authenticated, run `gh auth status`
  and ask the user to run `gh auth login` first.
- If the issue is already closed, say so and stop.
- If the issue is assigned to someone else, warn the
  user before proceeding.
- Keep comments professional — they are permanent,
  public record on the issue.
- Write commits in normal prose (not caveman style),
  even if caveman mode is active.
